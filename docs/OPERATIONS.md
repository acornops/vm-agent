# Operations

The AgentV is outbound-only. It connects to
`ACORNOPS_AGENT_PLATFORM_URL/api/v1/agent/connect`, performs a
`lifecycle/handshake`, sends heartbeats, uploads bounded host snapshots, and
serves strict JSON-RPC tool calls. It remains read-only unless local, remote,
and helper policy all enable `restart_service`.

Linux/systemd installs use `packaging/systemd/acornops-agentv.service` and
`/etc/acornops/agentv.env`. Keep the env file owned by `root:acornops-agent`
with mode `0640`.

For the initial bootstrap, both host `curl` and `/usr/bin/node` must already
trust the control-plane certificate. Install a private root in the host trust
store before onboarding. After installation, a root-managed PEM path in
`ACORNOPS_AGENT_ADDITIONAL_CA_BUNDLE_FILE` adds runtime trust without replacing
public roots or disabling certificate and hostname verification. Repair,
upgrade, and credential replacement preserve this setting.

## Runtime Requirements

- Node.js 22 or newer at `/usr/bin/node`, or a container image built from this
  repository. The installer validates the systemd runtime path and major version.
- Linux with systemd for `ACORNOPS_VM_COLLECTOR_MODE=live`.
- Network egress from the VM to the AcornOps control-plane WebSocket endpoint.
- A one-use enrollment command for initial installation, or an existing
  root-owned AgentV environment for repair and upgrade.
- HTTPS transport to the control plane. Plaintext `http://` requires the
  explicit local-development override and must not be used in production.

## Systemd Model

The main service runs as `acornops-agent` with readiness/watchdog notification,
`NoNewPrivileges`, private devices, kernel protections, restricted namespaces,
and explicit address families. The separate helper runs as root with no network
access and may write only its bounded action ledger.

Systemd starts Node as the tracked main process. Node invokes the fixed
`/usr/bin/systemd-notify` binary for bounded readiness and watchdog messages;
`NotifyAccess=all` permits those short-lived notifier children from this
service cgroup. Releases need no target-side compiler or native addon build.

Operational files:

- Unit: `packaging/systemd/acornops-agentv.service`
- Helper: `packaging/systemd/acornops-agentv-actions.socket` and `.service`
- Environment template: `packaging/systemd/agentv.env.example`
- Install helper: `packaging/systemd/install.sh`
- Secret-free transaction worker: `packaging/systemd/install-worker.sh`
- Boot recovery helper/unit: `packaging/systemd/acornops-agentv-install-recover`
  and `acornops-agentv-install-recovery.service`
- Uninstall helper: `packaging/systemd/uninstall.sh`

For normal onboarding, run only the exact version-pinned command generated by
the AcornOps management console. Initial and credential-replacement commands
carry a target-bound enrollment token that is single-use and expires after 15
minutes; the durable AgentV key is returned only to the root installer. The
copied command may remain in shell history, but its enrollment token is useless
after a successful exchange; clear the entry when host policy requires it.
Repair and upgrade commands reuse the matching root-owned environment. The
bootstrap verifies the archive checksum, records rollback state, and restores
the prior release and configuration when cutover fails. The token-bearing
bootstrap process is replaced by a worker whose arguments contain no
credentials. A successful normal handshake writes
`/run/acornops-agentv/authenticated`, which
the installer uses together with the protected control-plane transaction to
confirm cutover or rollback connectivity.

Credential replacement first authenticates provisionally. That connection has
no tools and cannot claim the target. Commit promotes the candidate credential,
keeps the prior credential in a 30-minute rollback grace period, then requires
the normally authenticated AgentV connection to become ready. Durable
credentials do not expire or rotate on a schedule.

Incomplete transaction state is root-only under
`/var/lib/acornops-agentv/install-transactions`. At boot, recovery queries the
protected transaction status. It retains a committed candidate, cancels and
restores an uncommitted candidate, and retries without changing credentials if
the control plane cannot be reached. Commit and rollback authorization expires
after one hour; the same protected secret can only read final status afterward,
which lets a host recover after a longer outage without reopening mutation. If
the 30-minute credential rollback grace has closed, recovery restores the
already-committed candidate because it is the only credential the control plane
still accepts.

If an installer reports that an incomplete transaction exists, run
`sudo systemctl start acornops-agentv-install-recovery.service` and inspect that
unit's journal. Do not delete the root-owned transaction directory while
recovery is pending.

The tag release workflow runs the complete systemd gate on a fresh
GitHub-hosted Ubuntu 24.04 VM before publishing. It exercises bootstrap,
authentication, same-version rerun, credential replacement, upgrade, rollback,
boot recovery, and uninstall preservation. Ubuntu 24.04 LTS is the only
qualified first-release host; other distributions require equivalent live
evidence before they can be documented as supported.

The installer adds `acornops-agent` to `systemd-journal` when that group exists.
Run `sudo acornops-agentv-doctor` to verify configuration, binaries, journal
access, filesystem collection, TLS, and optional helper policy. The wrapper
drops privileges before checking host access, so its result reflects the actual
`acornops-agent` service identity rather than root's permissions.

## Optional service restart

Writes are disabled by default. For production onboarding, select read-write
access in the management console and add each exact restartable `.service`
unit before generating the command. The enrollment-bound policy is returned
only to the root installer, which atomically writes
`/etc/acornops/agentv-actions.json`, sets
`ACORNOPS_AGENT_WRITE_ENABLED=true`, and enables
`acornops-agentv-actions.socket`. Repair preserves and validates the local
policy; token-backed replacement re-applies the enrollment snapshot. Both
restore the prior policy on failure. Globs, aliases, AgentV's own units,
arbitrary commands, sudo, and unrestricted `systemctl` are rejected. Editing
these files manually is not a supported way to change the control-plane policy.

For the Docker-only mock fixture, set both `ACORNOPS_AGENT_WRITE_ENABLED=true`
and `ACORNOPS_AGENT_MOCK_ACTIONS_ENABLED=true` to simulate a restart of its
single fixture service, `ssh.service`. This path never contacts systemd or a
host helper and is rejected outside mock collector mode.

## Logs And Diagnostics

Use journalctl for systemd installs:

```bash
journalctl -u acornops-agentv -f
```

The agent logs startup configuration without secrets, WebSocket connection status, handshake acknowledgement, snapshot upload summaries, snapshot collection failures, and WebSocket errors.

## Failure Modes

- Control plane unavailable: the agent reconnects with capped equal-jitter exponential backoff.
- Host adapter unavailable: collector health reports degraded/unavailable rather than a successful empty result.
- Oversized snapshot: optional entries are deterministically trimmed, then the snapshot is dropped if compressed bytes still exceed the negotiated hard limit.
- Ambiguous restart: the helper/executor reports `outcome: unknown`; the action is never marked retryable.
- Invalid configuration: startup fails fast with a clear environment-variable error.

## Rollback

Systemd installs can roll back atomically by replacing
`/opt/acornops/agentv/current` with a symlink to a preserved release and then
restarting the main service. Stop any currently active socket helper so the next
socket activation starts it from the selected release:

```bash
ln -s /opt/acornops/agentv/releases/<version> /opt/acornops/agentv/.rollback
mv -Tf /opt/acornops/agentv/.rollback /opt/acornops/agentv/current
systemctl restart acornops-agentv.service
systemctl stop acornops-agentv-actions.service
```

The action socket remains enabled and starts the selected helper on the next
request. Configuration, action policy, ledger, and prior releases are preserved
by both upgrade and uninstall.
